<section id="words">
  <h2>0. Words you will see a lot</h2>
  <table>
    <tr><th>Word</th><th>Simple meaning</th></tr>
    <tr><td><b>LiDAR</b></td><td>A spinning laser on the car roof. It measures the distance to things around the car and gives a cloud of 3D dots called a <b>point cloud</b>. It is very good at "where is it?" but sees no colour.</td></tr>
    <tr><td><b>Camera</b></td><td>Gives a normal picture with colour and detail. Good at "what is it?" but a single picture does not tell you how far away things are.</td></tr>
    <tr><td><b>BEV (bird's-eye view)</b></td><td>A map of the scene seen from straight above, like a game map. Cars on a road do not overlap in this view, so it is easy to work with.</td></tr>
    <tr><td><b>Feature</b></td><td>A list of numbers a neural network uses to describe something (a pixel, a point, a map cell).</td></tr>
    <tr><td><b>Voxel</b></td><td>A small 3D box of space, like a pixel but in 3D.</td></tr>
    <tr><td><b>Backbone / neck / head</b></td><td>Backbone: the main part that reads the input. Neck: tidies and combines its outputs. Head: the last part that gives the answer (boxes, labels, masks).</td></tr>
    <tr><td><b>Fusion</b></td><td>Mixing information from more than one sensor into a single result.</td></tr>
    <tr><td><b>CUDA op</b></td><td>A small program written for the GPU that is much faster than normal Python code. This repo has several, and they have to be compiled before you can run it.</td></tr>
    <tr><td><b>nuScenes</b></td><td>The public driving dataset the project is trained and tested on.</td></tr>
  </table>
</section>

<section id="why">
  <h2>1. The problem and the idea</h2>
  <p>A car has two kinds of "eyes", and each one is good at something different:</p>
  <ul>
    <li><b>Cameras</b> see colour and detail, so they know what something is, but they do not know how far away it is.</li>
    <li><b>LiDAR</b> knows exactly where things are in 3D, but it sees only sparse dots and no colour.</li>
  </ul>
  <p>We want the best of both. The hard part is that they describe the world in different ways: a camera gives a flat picture, LiDAR gives 3D dots.</p>

  <p><b>The older approach:</b> take each LiDAR point and give it the colour of the camera pixel it lines up with. The problem is that a camera image has millions of pixels, but LiDAR has only a few thousand points. So only a tiny part of the picture (about 5%) ever gets used, and the rest is thrown away. That makes it hard to understand what things are, like where the road or a crosswalk is.</p>

  <p><b>BEVFusion's idea:</b> turn <i>both</i> sensors into the same top-down map (the BEV), then mix the two maps. Nothing from the camera is thrown away, and a top-down map is a good place to find cars, people and road markings.</p>
  <div class="note">The same fused map can be used for different jobs. For <b>detection</b> the result is 3D boxes around objects. For <b>map segmentation</b> the result is a coloured map (road, crosswalk, and so on). The only part that changes is the last piece, the head.</div>
  <p>One more trick: turning camera pictures into a top-down map was very slow, so the authors wrote a fast GPU program for it, called <code>bev_pool</code>. That is why this repo has compiled code in it.</p>
</section>

<section id="camera">
  <h2>3. Camera path: turning a flat picture into 3D</h2>
  <p>A picture does not say how far away anything is. The method used here is called <b>Lift-Splat-Shoot (LSS)</b>. It lives in <code>mmdet3d/models/vtransforms/</code>. Here are the steps for each camera:</p>
  <ol>
    <li><b>Find patterns.</b> A network called Swin-T reads the image and a neck tidies the result. The output is a smaller "feature picture", 32×88 for a 256×704 image (one-eighth of the size).</li>
    <li><b>Make a ray of guesses.</b> For every pixel the code imagines a straight line going out from the camera. On that line it puts 118 possible distances, from 1 m to 60 m in steps of 0.5 m. (<code>create_frustum</code> in <code>base.py</code>)</li>
    <li><b>Guess the distance (the "lift").</b> A small network gives each pixel two things: (a) a set of chances for each of the 118 distances ("probably 20 m away"), and (b) an 80-number description of what the pixel looks like. Then it gives each distance a copy of the description, <b>scaled by how likely that distance is</b>. (<code>lss.py</code>, <code>get_cam_feats</code>)</li>
    <li><b>Find where each guess is in the real world.</b> Using the camera's position and lens settings, the code works out the real 3D position of every guess. It also undoes any picture or 3D changes made while training, so everything stays lined up. (<code>get_geometry</code> in <code>base.py</code>)</li>
    <li><b>Drop them on the map (the "splat").</b> All the guesses from all 6 cameras are dropped onto the top-down map and added up per square. See the next section.</li>
  </ol>

  <h3>Try it: how the distance guess works</h3>
  <p>For one pixel the network gives a score for every distance, and these are turned into chances. If the network is <b>sure</b>, one distance gets almost all the weight. If it is <b>unsure</b>, the weight is spread out along the whole ray.</p>
  <div class="ctrl"><label>How sure <input type="range" id="conf" min="0.5" max="12" step="0.1" value="4"></label>
  <label>Real distance <input type="range" id="tdep" min="2" max="58" step="1" value="22"> <span id="tdv">22 m</span></label></div>
  <div class="bars" id="bars"></div>
  <p style="font-size:.85rem;color:var(--muted)">Each bar is one of the 118 distances (1 m to 60 m). The pixel's 80 numbers are multiplied by the height of each bar.</p>

  <details><summary>The different versions: LSS, DepthLSS, BEVDepth</summary>
    <p><code>LSSTransform</code> guesses distance using the picture alone. <code>DepthLSSTransform</code> (used in the fusion setup) also projects the LiDAR points onto each picture to make a rough distance map, and gives it to the network as a hint. So the camera path gets help from the LiDAR. That projection code is in <code>BaseDepthTransform.forward</code> (<code>base.py</code>, around line 238). The <code>BEVDepth</code> versions also train the distance guess directly, which is what <code>use_depth_loss</code> in <code>bevfusion.py</code> checks for.</p>
  </details>
</section>

<section id="bevpool">
  <h2>4. BEV pooling: the step that had to be fast</h2>
  <p>After the "lift", one frame has about <b>2 million</b> small feature lists, each with a 3D position. The "splat" step has to put each one into a square of the top-down map and add together all the ones that land in the same square.</p>
  <p>Done in the simple way, this was very slow. The repo uses a faster way (<code>mmdet3d/ops/bev_pool/</code>):</p>
  <ol>
    <li>Work out which square each point belongs to, and throw away points outside the map (<code>base.py</code>, the <code>bev_pool</code> method, around line 149).</li>
    <li><b>Sort the points by square</b>, so all the points for one square sit next to each other.</li>
    <li>A GPU program (<code>bev_pool_cuda.cu</code>) lets <b>one worker handle one square</b>. It adds up that square's points and writes one answer. Training also works, because the backward step does the reverse.</li>
  </ol>
  <p>The Python side is <code>bev_pool.py</code>. The class <code>QuickCumsumCuda</code> finds where each group starts and ends, then calls the compiled program <code>bev_pool_ext</code>. The paper says this made the step about 40 times faster.</p>

<section id="lidar">
  <h2>5. LiDAR path: working only where there are points</h2>
  <p>A LiDAR scan is a cloud of dots, and most of the space around the car is empty. So the code is built to skip the empty parts:</p>
  <ol>
    <li><b>Voxelize</b> (<code>mmdet3d/ops/voxel/</code>): cut the space into tiny boxes, 0.075 m × 0.075 m × 0.2 m. Over a ±54 m range this gives a grid of 1440 × 1440 × 41 boxes, but only about 100,000 of them hold any points. Each box keeps the average of its points (<code>voxelize</code> in <code>bevfusion.py</code>, around line 192).</li>
    <li><b>SparseEncoder</b> (<code>backbones/sparse_encoder.py</code>): a 3D network that does its work <i>only inside the boxes that have points</i>. It uses a library called <code>spconv</code>, whose code is copied into <code>mmdet3d/ops/spconv/</code>. Four stages shrink the grid step by step.</li>
    <li><b>Flatten the height.</b> The "up" direction is merged into the channels, which leaves a flat top-down map. Its 256 channels match what the fuser expects (<code>in_channels: [80, 256]</code>).</li>
  </ol>
  <div class="note warn"><b>Why you should care:</b> the sparse 3D code and the voxel code are the GPU programs most likely to break on a new graphics card (your RTX 5070 Ti) and a newer PyTorch. They are the hardest part of making this repo run on your machine.</div>
</section>

<section id="fusion">
  <h2>6. Mixing the maps, and getting the answer</h2>
  <h3>Fusion: <code>fusers/conv.py</code></h3>
  <p>This is only a few lines. Stack the two maps on top of each other (80 + 256 = 336 channels), then pass them through one small convolution, normalisation and ReLU to get 256 channels. It works because both maps already cover the same area and the same squares, which is the whole point of using BEV.</p>
<pre>nn.Conv2d(sum(in_channels), out_channels, 3, padding=1, bias=False)
nn.BatchNorm2d(out_channels);  nn.ReLU(True)</pre>

  <h3>Decoder</h3>
  <p>A 2D network named <code>SECOND</code> (two stages, 128 and 256 channels) and a neck named <code>SECONDFPN</code> that brings both back to the same size and joins them into <b>512 channels</b> on a 180 × 180 map. The detection head expects exactly this (<code>in_channels: 512</code>).</p>

  <h3>Heads (the part that gives the answer)</h3>
  <table>
    <tr><th>Head</th><th>File</th><th>Job</th><th>How it works</th></tr>
    <tr><td><code>TransFusionHead</code></td><td><code>heads/bbox/transfusion.py</code></td><td>Find 3D objects</td><td>Picks the 200 most promising spots on the map, then improves each guess with a small transformer (8 attention heads). Each spot gives the centre, height, size, rotation and speed of an object. In training, guesses are matched to the real objects one-to-one (a "Hungarian assigner", like the DETR model), not with preset box shapes.</td></tr>
    <tr><td><code>CenterHead</code></td><td><code>heads/bbox/centerpoint.py</code></td><td>Find 3D objects</td><td>Used by the camera-only baselines. It marks the centre of each object on a heat map and predicts the box from there.</td></tr>
    <tr><td>Map head</td><td><code>heads/segm/vanilla.py</code></td><td>Colour the map</td><td>For every square it says which map classes apply: road, crossing, walkway, stop line, car park, divider.</td></tr>
  </table>
</section>

<section id="config">
  <h2>7. How the settings files (configs) work</h2>
  <p>Settings are YAML files read by <code>torchpack</code>. The important idea: <b>a config also loads every <code>default.yaml</code> in the folders above it</b>. The detection fusion file is tiny:</p>
<pre># configs/nuscenes/det/transfusion/secfpn/camera+lidar/swint_v0p075/convfuser.yaml
model:
  fuser:
    type: ConvFuser
    in_channels: [80, 256]
    out_channels: 256</pre>
  <p>All the rest comes from these files, in this order:</p>
  <table>
    <tr><th>File</th><th>What it adds</th></tr>
    <tr><td><code>configs/default.yaml</code></td><td>random seed, logging, saving checkpoints, fp16 (half precision), <code>max_epochs: 20</code>, the training runner</td></tr>
    <tr><td><code>nuscenes/default.yaml</code></td><td>dataset, map range, voxel size, data tricks, the 10 object classes, the 6 map classes, the data pipelines</td></tr>
    <tr><td><code>det/default.yaml</code></td><td>model type <code>BEVFusion</code>, radar defaults, a detection data pipeline</td></tr>
    <tr><td><code>transfusion/default.yaml</code></td><td>the <code>TransFusionHead</code> and its matching rules</td></tr>
    <tr><td><code>secfpn/default.yaml</code></td><td>the SECOND + SECONDFPN decoder, AdamW optimizer, cyclic learning rate</td></tr>
    <tr><td><code>camera+lidar/default.yaml</code></td><td>camera neck + DepthLSSTransform, LiDAR voxelize + SparseEncoder, <code>max_epochs: 6</code></td></tr>
    <tr><td><code>swint_v0p075/default.yaml</code></td><td>Swin-T image network, voxel size 0.075, range ±54 m, cosine learning rate</td></tr>
  </table>
  <p>A value like <code>${image_size}</code> is replaced by the value set elsewhere. You can also change any value from the command line, for example <code>--model.encoders.camera.backbone.init_cfg.checkpoint path.pth</code>.</p>
  <p>The words after <code>type:</code> (<code>BEVFusion</code>, <code>ConvFuser</code>, <code>SparseEncoder</code>, ...) are names in a <b>registry</b>: a lookup table filled by lines like <code>@FUSERS.register_module()</code>. <code>mmdet3d/models/builder.py</code> uses it to turn a name in the YAML into a Python class.</p>
</section>

<section id="train">
  <h2>8. How the model is trained</h2>
  <ol>
    <li><b>Data:</b> nuScenes has 1000 driving scenes. Each frame has 6 camera images and a 32-beam LiDAR scan. <code>tools/create_data.py</code> prepares the files and a database of real objects.</li>
    <li><b>Data tricks (augmentation)</b> in <code>datasets/pipelines/</code>: change the pictures (resize, rotate, flip) with <code>ImageAug3D</code>, which saves the change as <code>img_aug_matrix</code>; change the 3D scene (scale, rotate, shift) with <code>GlobalRotScaleTrans</code>, which saves <code>lidar_aug_matrix</code>; and paste extra objects from the database (<code>ObjectPaste</code>). The two saved matrices are how <code>get_geometry</code> keeps camera and LiDAR lined up after the changes.</li>
    <li><b>Train in two steps:</b> first train a LiDAR-only model. Then train the fusion model starting from it (<code>--load_from pretrained/lidar-only-det.pth</code>), using an image network that was already trained on the nuImages dataset. The fusion setup trains for 6 epochs at learning rate 2e-4.</li>
    <li><b>Start it:</b> <code>torchpack dist-run -np 8 python tools/train.py &lt;config&gt;</code>. It uses MPI to start one process for each GPU.</li>
  </ol>
</section>

<section id="paper">
  <h2>9. What the paper adds</h2>
  <p>This section uses the paper <i>BEVFusion: Multi-Task Multi-Sensor Fusion with Unified Bird's-Eye View Representation</i> (MIT, arXiv 2205.13542, ICRA 2023). I read it from the arXiv web version, so section numbers are the paper's own, but I could not tell which version it was. Where I could not find something in the text I say <b>not found</b> instead of guessing.</p>

  <h3>9.1 Why not paint the LiDAR points? (Sec. I, III-A)</h3>
  <ul>
    <li><b>Camera onto LiDAR points (the older way):</b> with a 32-beam LiDAR only about <b>5%</b> of the camera's information lands on a LiDAR point. The other 95% is lost. The paper says this loses meaning (what things are). It gets worse with sparser LiDAR or radar. That is why this older way does badly at colouring a map.</li>
    <li><b>LiDAR onto the picture:</b> you get a thin, patchy distance picture. Two pixels that sit next to each other in the picture can be far apart in real 3D, so it loses shape.</li>
    <li><b>Mixing deep inside the network</b> (FUTR3D, TransFusion) has the same problem.</li>
    <li><b>BEV avoids both.</b> Putting LiDAR on a top-down map only flattens the height, so the shape is kept. Putting the camera on a top-down map keeps <i>all</i> the camera information. The authors say this is why a smaller camera image is enough, which saves computing.</li>
  </ul>

  <h3>9.2 Numbers for the camera transform and BEV pooling (Sec. III-B)</h3>
  <table>
    <tr><th>What</th><th>Value from the paper</th><th>Where in this repo</th></tr>
    <tr><td>Cameras and image size</td><td>6 cameras, 256 × 704</td><td><code>image_size: [256, 704]</code></td></tr>
    <tr><td>Feature picture (1/8 size)</td><td>32 × 88</td><td><code>feature_size</code></td></tr>
    <tr><td>Distance guesses</td><td>1 to 60 m, every 0.5 m, so <b>118</b></td><td><code>dbound: [1.0, 60.0, 0.5]</code></td></tr>
    <tr><td>Guess points per frame</td><td>6 × 32 × 88 × 118 = <b>1,993,728</b> (about 2 million), "two orders of magnitude" more than a LiDAR scan</td><td>the tensor made by <code>get_cam_feats</code></td></tr>
    <tr><td>Slow way</td><td>over 500 ms on an RTX 3090, while the rest of the model took about 100 ms; over 80% of the run time; up to 2 s per scene in the original LSS code</td><td>—</td></tr>
    <tr><td>Fast way</td><td>finding squares: 17 → 4 ms; adding up: 500 → 2 ms; the whole step: about <b>12 ms</b> (around 10% of the total). The paper calls this <b>40× faster</b></td><td><code>ops/bev_pool/</code></td></tr>
  </table>
  <p><b>The two tricks, simply:</b></p>
  <ol>
    <li><b>Do the work ahead of time.</b> The camera positions and lens settings do not change, so the real position and map square of every guess point can be worked out once. Sort the points by square and remember their order. Then at run time you only re-order the features. <i>(In this repo the positions are recalculated on every forward pass in <code>get_geometry</code>, and the sorting happens in the Python part of <code>bev_pool.py</code>, so I would not assume the repo saves this between frames.)</i></li>
    <li><b>One worker per square.</b> The old way (from LSS) added up all points in one long running total and then subtracted at the borders. That needed many steps and wasted work on totals nobody used. BEVFusion gives each map square its own GPU worker. The worker adds up only its own points and writes one number. There is no waiting on other workers and no wasted totals. In the repo, <code>QuickCumsumCuda</code> computes <code>interval_starts</code> and <code>interval_lengths</code>, and the GPU program does the sums.</li>
  </ol>
  <p>The paper stresses that this gives the <b>exact same answer</b>. Two similar projects at the time (BEVDet and M2BEV) got speed by dropping points or assuming equal distances, which changes the result.</p>

  <h3>9.3 Mixing the maps, and a known weak spot (Sec. III-C)</h3>
  <p>Because both sensors are on the same map, mixing is simple, for example just stacking them. Then a small convolution network with "a few residual blocks" cleans up. The reason for it: the camera map depends on <i>guessed</i> distances, so it can sit a little off from the LiDAR map. The convolutions fix small shifts like that. The paper's own idea for a better fix is to train the distance guess with real distances, and it leaves that for future work.</p>
  <div class="note">In this repo the "mix and clean up" part is split in two: <code>ConvFuser</code> (stack + one 3×3 convolution) and then the <code>SECOND</code> decoder, which gives the deeper convolutions. The name "ConvFuser" is the repo's, and I did not find it in the paper text. The <code>BEVDepth</code>-style versions in <code>vtransforms/</code> are the repo's way of training the distance guess directly, which the paper left for later.</div>

  <h3>9.4 The heads (Sec. III-D, IV-B)</h3>
  <ul>
    <li><b>Detection:</b> the paper describes a heat map for each class that marks object centres (like CenterPoint), plus parts that predict size, rotation and speed. The released detection setup actually uses <code>TransFusionHead</code>, and the camera-only baselines use <code>CenterHead</code>. Both are in <code>heads/bbox/</code>.</li>
    <li><b>Map colouring:</b> treated as several separate yes/no questions, one for each class, because map classes overlap (a crosswalk is also part of the road). Trained with focal loss (a loss that focuses on hard examples). It is scored on a 100 m × 100 m area around the car. Six classes: drivable area, pedestrian crossing, walkway, stop line, car park, divider.</li>
    <li>Before each head, the fused map is resized to that task's area and detail level using bilinear sampling. The LiDAR box size is 0.075 m for detection and 0.1 m for map colouring.</li>
  </ul>

<section id="run">
  <h2>12. Running it: what to know</h2>
  <div class="card">
    <p><b>The original setup needs:</b> Python 3.8, PyTorch 1.10.2 or older, mmcv 1.4.0, mmdet 2.20.0, CUDA 11.x, OpenMPI + torchpack, and a compiler to build the GPU programs.</p>
    <p><b>Newest graphics cards (RTX 50-series):</b> CUDA 11.x and PyTorch 1.10 cannot use them, so the original setup will not run. You need PyTorch 2.7 or newer with CUDA 12.8 or newer. That means updating the old mmcv 1.x code, rebuilding the GPU programs for the new PyTorch, and replacing the old copy of <code>spconv</code> and the MPI launcher.</p>
    <p><b>Memory:</b> the paper trains on 8 GPUs. A 12 GB card would need a small batch size and probably smaller images to train. Running a finished model (inference) is more realistic.</p>
